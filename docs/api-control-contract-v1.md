# API-First Puppy Control Contract (v1)

This document defines the canonical command/ack/session contract for a device app that is controlled only through API-issued commands.

## Principles

- API is the only authority that creates control intents.
- Device app is an execution client.
- Every command has a lifecycle and audit trail.
- Screen-share media path can be peer-to-peer WebRTC, but session authorization comes from API.

## Command Envelope

```json
{
  "version": 1,
  "command_id": "uuid",
  "device_id": "dev_123",
  "handler_id": "hdl_abc",
  "action": "puppy.checkin.request",
  "priority": "normal",
  "created_at": "2026-05-26T18:00:00Z",
  "expires_at": "2026-05-26T18:05:00Z",
  "idempotency_key": "uuid-or-stable-key",
  "params": {}
}
```

### Required fields

- version: integer, currently 1.
- command_id: unique UUID generated by API.
- device_id: target device identity.
- action: command action key.
- created_at: RFC3339 UTC timestamp.
- expires_at: RFC3339 UTC timestamp.
- params: action-specific object.

### Optional fields

- handler_id: actor identity.
- priority: low | normal | high | emergency.
- idempotency_key: allows safe retries.

## Ack/Event Envelope

```json
{
  "version": 1,
  "command_id": "uuid",
  "device_id": "dev_123",
  "status": "SUCCEEDED",
  "stage": "FINAL",
  "timestamp": "2026-05-26T18:00:03Z",
  "error_code": null,
  "error_message": null,
  "telemetry": {
    "latency_ms": 124,
    "path": "accessibility"
  }
}
```

### status values

- RECEIVED
- RUNNING
- SUCCEEDED
- FAILED
- EXPIRED
- REJECTED

### error_code examples

- unsupported_action
- invalid_params
- capability_missing
- permission_missing
- session_invalid
- execution_timeout
- execution_error

## screen.input.lock.set params

```json
{
  "enabled": true,
  "mode": "strict",
  "allow_remote_input": true,
  "session_id": "ssn_456",
  "ttl_sec": 900,
  "reason": "handler_control_window"
}
```

### mode values

- advisory: show lock UI and warning; best-effort local deterrence only.
- overlay_guard: full-screen touch-swallow overlay while session is active.
- strict: root/device-owner assisted hard lock (implementation-defined, capability-gated).

## Touch lock behavior contract

This solves: block local touches while still allowing website control.

### Capability tiers

- tier 0 (no root, no special owner privileges): advisory only is guaranteed.
- tier 1 (accessibility + overlay): overlay_guard can block most local interaction, but may also intercept injected tap targets depending on implementation; not guaranteed for arbitrary app control.
- tier 2 (root or privileged device-owner path): strict lock can disable physical touch path while preserving command-driven input injection path.

### Device response requirements

On screen.input.lock.set(enabled=true):

1. Validate active session_id and token.
2. Validate requested mode against device capability.
3. If unsupported, return FAILED with capability_missing and include supported modes in telemetry.
4. If supported, set lock and report SUCCEEDED.

On screen.input.lock.set(enabled=false):

1. Remove lock immediately.
2. Return SUCCEEDED.

## Recommended policy

- Never enable lock without an active screen session.
- Auto-release lock when session stops, expires, or heartbeat fails.
- Enforce one active control session per device unless explicit override.
- Log all lock transitions to timeline.

## Practical implementation note for this repo

Current remote input path uses WebRTC data channel messages forwarded to native injectTap.

- Flutter path: flutter_app/lib/services/screen_share_service.dart
- Flutter channel: flutter_app/lib/channels/screen_share_channel.dart
- Native bridge (root app): app/src/main/java/com/tpeapp/bridge/ScreenShareChannel.kt
- Accessibility injector: app/src/main/java/com/tpeapp/review/RemoteControlService.kt

The standalone Flutter host now supports root-based tap injection for com.tpeapp/screen_share in flutter_app/android/app/src/main/kotlin/com/example/tpe_app/StandaloneTpeHost.kt. On non-rooted standalone builds, remote tap injection returns an explicit UNAVAILABLE error.

## Backward compatibility

Legacy actions may continue during migration:

- REQUEST_CHECKIN -> puppy.checkin.request

Device should support both for a transition window and emit canonical ACK envelopes for both.

## Vault command params and telemetry

### vault.entries.list params

```json
{}
```

Success ACK telemetry includes:

- vault_count: integer
- vault_entries: array of redacted entries (`id`, `site`, `username`, `notes`, `locked_until`, `is_locked`)

### vault.entry.add params

```json
{
  "site": "example.com",
  "username": "it@example.com",
  "password": "required",
  "notes": "optional"
}
```

Success ACK telemetry includes `vault_entry_id`.

### vault.entry.update params

```json
{
  "id": "entry_uuid",
  "site": "optional",
  "username": "optional",
  "password": "optional",
  "notes": "optional"
}
```

Success ACK telemetry includes `vault_entry_id` and `updated=true`.

### vault.entry.delete params

```json
{
  "id": "entry_uuid"
}
```

Success ACK telemetry includes `vault_entry_id` and `deleted=true`.

### vault.entry.lock params

```json
{
  "id": "entry_uuid",
  "ttl_sec": 900
}
```

### vault.entries.lock_all params

```json
{
  "ttl_sec": 900
}
```

For both lock actions, success ACK telemetry includes `locked_for_sec`.

### vault.entries.import params

```json
{
  "entries": [
    {
      "site": "example.com",
      "username": "it@example.com",
      "password": "required",
      "notes": "optional"
    }
  ]
}
```

Success ACK telemetry includes `inserted` and `requested`.

### vault.password.reveal params

```json
{
  "id": "entry_uuid",
  "reason": "handler verification"
}
```

Success ACK telemetry includes `vault_entry_id` and `password`.

Failure modes include:

- `execution_error` with rate-limit detail when reveal cooldown is active.
- `execution_error` when reason policy rejects the request.
